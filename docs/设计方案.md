# 麦门膳食师（McDiet Plan）设计方案

> 一句话卖点：**反向《大号的我》—— 连吃一周麦当劳，也能科学达成你的身材目标。**
>
> 基于麦当劳中国 MCP 能力开发的参赛 Skill ｜ 麦当劳程序员创意开发大赛

---

## 1. 项目定位

### 1.1 叙事钩子

2004 年纪录片《Super Size Me（大号的我）》中，导演连吃 30 天麦当劳，健康指标全线崩盘。本项目用麦当劳自己公开的营养数据，证明它的反面：**只要输入身体数据和目标，一周三餐全吃麦当劳，也能落在科学的营养区间内。**

这个叙事天然适配 1024 程序员节赛事：标题即梗、有算法含量、用官方数据"打脸"刻板印象，具备 GitHub 传播所需的全部要素。

### 1.2 一段话描述

用户输入性别、年龄、身高、体重、活动量、目标（减脂/增肌/维持）和预算，Skill 调用麦当劳 MCP 的营养数据与菜单数据，运行多约束求解器，生成**一周 7 天 × 3 餐的"全麦门"饮食计划**，并渲染成一张可交互的可视化网页。此后每天用户"打卡"实际吃了什么，Skill 动态调整剩余餐次的推荐——它不是一次性计算器，而是一个陪伴 7 天的饮食教练。

### 1.3 目标用户

- 想减脂/控体重、但讨厌水煮鸡胸的打工人（主力）
- 每天中午纠结"吃什么"的写字楼白领（麦当劳门店密度高，决策成本最低）
- 程序员群体（比赛受众，对"优化问题"叙事敏感）

### 1.4 差异化

| 维度 | 市面上常见参赛项目 | 本项目 |
|---|---|---|
| 用到的 MCP 工具 | 点餐、优惠券（红海） | **营养数据 Tool**（几乎无人用）+ 点餐 |
| 技术含量 | 提示词编排 | 多约束优化求解（纯 Python，零重依赖） |
| 使用周期 | 一次性对话 | **7 天闭环**，每天有理由回来用 |
| 可视化 | 聊天文本 | 自带网页模板：周计划、营养雷达图、体重预测曲线 |

## 2. 产品形态与用户旅程

### 2.1 形态

**WorkBuddy Skill（SKILL.md）+ Python 求解核心 + 单文件网页模板。**

- 核心求解逻辑用 Python 实现，可独立运行、可测试；
- SKILL.md 指导 AI 完成整个编排：收集数据 → 调 MCP → 跑求解器 → 注入网页模板 → 打开预览；
- 网页是单文件 HTML（内嵌 CSS/JS），数据以 JSON 注入，AI 唤起即可预览，用户也可双击本地打开、随手分享。

### 2.2 用户旅程

**第一次使用（生成计划）**

1. 用户在 WorkBuddy 对话框说："我要开启一周麦麦挑战"。
2. AI 按引导收集：性别 / 年龄 / 身高 / 体重 / 活动量（久坐~高强度五档） / 目标（减脂、维持、增肌） / 可接受日预算 / 忌口与过敏。
3. AI 调用 MCP 拉取营养数据与当前可售菜单，缓存到本地（首次之后不再重复请求）。
4. AI 运行求解器，得到 7×3 餐计划 + 每日营养汇总 + 价格汇总。
5. AI 将结果注入网页模板，打开预览。用户看到：周计划日历、每日热量进度条、三大宏量营养雷达图、7 天体重预测曲线、总花费与预算对比。

**每日打卡（7 天闭环）**

1. 第二天用户说："打卡，中午吃了麦辣鸡腿堡套餐"。
2. AI 把实际餐品匹配到营养库，更新状态文件。
3. 计算当日已摄入与剩余"热量预算"，重新求解今天剩余餐次和明天计划（早上超了就推荐板烧鸡腿堡而不是麦香鱼早餐）。
4. 网页刷新：打卡进度 +1，预测曲线根据实际摄入重算，给出一句话反馈（"今天还剩 620 kcal 预算，晚餐推荐…"）。

**收尾**

7 天结束后生成总结页：完成度、实际 vs 计划体重变化、营养达标率、总花费，用户可一键分享截图。

## 4. 核心算法设计

### 4.1 目标热量与宏量（输入 → 每日目标）

- **BMR**：Mifflin-St Jeor 公式
  - 男：`10×体重(kg) + 6.25×身高(cm) − 5×年龄 + 5`
  - 女：同上，末项 `−161`
- **TDEE** = BMR × 活动系数（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高度 1.725 / 极高 1.9）
- **目标热量**：减脂 = TDEE − 15%（设 1200 kcal 下限保护），维持 = TDEE，增肌 = TDEE + 10%
- **宏量目标**：蛋白质 = 1.6 g/kg（减脂）/ 1.4 g/kg（维持）/ 1.8 g/kg（增肌）；脂肪 ≥ 20% 总热量；碳水化合物补足；**钠 ≤ 2300 mg/天**（麦当劳餐的最大坑，作为硬约束展示）

### 4.2 求解问题形式化

给定候选餐品库 `F`（含每 100g 或每份的热量/蛋白/脂肪/碳水/钠/价格）：

- 决策变量：7 天 × 3 餐 × 每餐 2~4 个单品的选择
- 硬约束：每日热量 ∈ [目标−5%, 目标+8%]；钠 ≤ 2300 mg；忌口排除；单餐价格 ≤ 预算/3（P2）
- 软目标（加权最小化）：
  `J = w1·|蛋白缺口| + w2·|脂肪下限差| + w3·多样性惩罚 + w4·钠超标惩罚`
- 多样性惩罚：同一天内不重复单品；相邻两天主餐不重复；全周同单品 ≤ 3 次

### 4.3 求解策略（零重依赖，纯标准库）

1. **候选组合枚举**：按"主餐 + 小食 + 饮料"结构预生成每餐候选组合（饮料优先 0 卡：无糖可乐/零度糖浆咖啡），单餐候选控制在数百量级；
2. **贪心构造**：每天按热量目标/3 逐餐挑选综合评分最优组合；
3. **局部搜索**：随机重启（~200 次）+ 邻域交换（换某天某餐的组合），接受目标函数更优解；
4. 复杂度可控（毫秒级），不引入 PuLP/OR-Tools，保证"clone 即跑"。

### 4.4 打卡动态调整

- 用户打卡实际餐品后，当日剩余热量预算 = 日目标 − 已摄入（宏量同理）；
- 剩余餐次在"剩余预算"约束下重新求解；
- 已过天数的偏差被滚动摊销到未来天数（若连续超支，后续几天自动向目标下限靠拢），预测曲线同步重算。

## 5. 系统架构

### 5.1 模块图

```
WorkBuddy 对话（AI 编排层，由 SKILL.md 驱动）
        │
        ├── MCP 工具调用（streamablehttp → mcp.mcd.cn）
        │     list-nutrition-foods / query-meals / query-meal-detail
        │     calculate-price / auto-bind-coupons / create-order（P2）
        │
        ├── Python 求解核心（solver/）
        │     nutrition.py   营养库加载、缓存合并、忌口过滤
        │     targets.py     BMR/TDEE/宏量目标计算
        │     planner.py     组合枚举 + 贪心 + 局部搜索
        │     checkin.py     打卡解析辅助、状态读写、动态重排
        │
        ├── 数据层
        │     data/nutrition_cache.json   MCP 营养数据缓存 + 人工补充
        │     state.json                  用户档案 + 计划 + 打卡流水
        │     plan.json                   求解结果（网页数据源）
        │
        └── web/template/plan.html        单文件网页模板（Chart.js CDN）
              AI 将 plan.json 注入占位符 → 生成 plan.html → 打开预览
```

### 5.2 MCP 工具映射（对应 MCP_INTEGRATION.md 素材）

| Tool | 用途 | 调用时机 |
|---|---|---|
| `list-nutrition-foods` | 核心数据源：热量/蛋白/脂肪/碳水/钠 | 首次运行拉取并缓存 |
| `query-meals` | 当前门店可售菜单，过滤不可售单品 | 生成计划前 |
| `query-meal-detail` | 套餐组成与可替换项 | 细化套餐配置 |
| `calculate-price` | 价格约束（P2） | 预算求解 |
| `auto-bind-coupons` | 领券省钱（P2） | 下单前 |
| `create-order` / `query-my-account` | 一键下单 / 积分联动（P2） | 可选 |

工程约定：所有 MCP 数据**先读缓存、定期刷新**，规避 600 次/分钟限流；缓存文件附数据拉取日期。

### 5.3 网页模板设计（单文件 plan.html）

- 技术约束：单 HTML、内嵌 CSS/JS、Chart.js 走 CDN（cdnjs）；数据注入点为 `<script id="plan-data" type="application/json">{...}</script>`，AI 只替换该块；
- 视觉：麦当劳式暖色（#FFC72C 黄 + #DA291C 红）点缀，浅色底，克制不花哨；
- 区块自上而下：
  1. 头部：挑战标题 + 用户档案徽章 + 第 N 天进度；
  2. 今日视图：三餐卡片（餐品图占位、热量、蛋白/脂肪/碳水/钠四项微条）、今日剩余预算条、主 CTA"打卡这一餐"；
  3. 周视图：7×3 计划表格 + 每日热量柱状图（实际 vs 计划叠加）；
  4. 营养雷达图：七日均值 vs 目标；
  5. 体重预测曲线：计划预测线 + 打卡实际点；
  6. 底部：免责声明 + "Powered by 麦当劳 MCP"。
- 打卡交互：页面上勾选 → localStorage 暂存 + 提示"回到 WorkBuddy 说'打卡'完成同步"（网页本身不持有 MCP Token，规避安全风险）。

## 6. 数据设计（核心 Schema 摘要）

**nutrition_cache.json**
```json
{
  "fetched_at": "2026-10-10",
  "items": [
    { "code": "XXX", "name": "板烧鸡腿堡", "category": "主餐",
      "serving": "1 份", "kcal": 415, "protein_g": 22, "fat_g": 17,
      "carb_g": 41, "sodium_mg": 890, "price": 24.5, "source": "mcp" }
  ]
}
```
`source` 区分 `mcp`（官方数据）与 `manual`（人工补充），网页与 README 注明数据口径。

**state.json**
```json
{
  "profile": { "gender": "M", "age": 28, "height_cm": 175, "weight_kg": 72,
                "activity": "light", "goal": "cut", "budget": 60, "avoid": ["牛肉"] },
  "targets": { "kcal": 2050, "protein_g": 115, "sodium_max_mg": 2300 },
  "start_date": "2026-10-12",
  "plan":   { "2026-10-12": { "breakfast": [], "lunch": [], "dinner": [] } },
  "checkins": { "2026-10-12": { "lunch": [ { "code": "XXX", "qty": 1 } ] } },
  "weight_log": { "2026-10-12": 72.0 }
}
```

## 8. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 营养 Tool 数据覆盖不全（早餐/酱料/饮料缺项） | 高 | P0 阶段先全量拉取做覆盖度盘点；缺项走人工补充表并标注 `manual`；饮品优先映射"0 卡系列" |
| 打卡餐品无法精确匹配 | 中 | 模糊匹配（名称包含 + 类别 + 热量相近）→ AI 读菜单列表人工裁决 → 允许"大致摄入量"手输兜底 |
| 被质疑"鼓励不健康饮食" | 中 | 定位为"营养信息透明化工具"，硬约束钠上限，显著免责声明，提供"维持"目标选项 |
| Star 传播不足 | 中 | 首屏 GIF + 真人 7 天实测数据（自愿）+ 中英双语 README + 项目名带梗 |
| MCP 限流 / Token 泄露 | 低 | 缓存优先策略；SKILL.md 明确禁止把 Token 写入任何生成文件 |
